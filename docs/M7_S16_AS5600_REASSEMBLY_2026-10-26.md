## Updated firmware source
On the existing `feature/m7-s15-ps2-controls-restoration-staged` branch, `Core/Src/main.c` now uses all six reported values. CENTER is a fixed compile-time target. MIN/MAX initialize the runtime RAM variables and can later be updated by a fully successful SELECT scan; no Flash persistence is provided.

The old calibration validator required RIGHT MIN RAW >=2200 and could not accept the new 191 count value. `Steering_PositionGeometryValid` now checks direction-dependent CENTER bracketing with at least 60 counts from each endpoint, a 250–1250 RAW total stroke, and unwrapped monotonic RAW values. This common check is used for both SELECT calibration acceptance and normal position acceptance. If a future sensor mounting crosses 4095 -> 0, the existing noncircular M7-S10 soft-limit logic needs redesign before such a scan can be accepted.

Existing M7-S10 manual soft clearance settings were **not changed**: LEFT has 100 RAW margin (SOFT_MIN 2197, SOFT_MAX 1474); RIGHT has 40 RAW margin (SOFT_MIN 231, SOFT_MAX 942). Coasting clearance has not been verified on hardware after reassembly.

The S11 strict global AS5600 hard-envelope checker now uses each motor's NEW CENTER as signed shortest-delta reference and NEW MIN/MAX with 8 RAW tolerance. It additionally rejects invalid geometry. The separate 64-RAW range used by bounded position/escape algorithms is preserved. Unexpected NC contact and AS5600 communication faults still stop the vehicle. Arming is unchanged and remains disabled at boot: `steer_safety_motion_permit=0`, `steer_manual_enable=0`, `steer_pos_enable=0`, `steer_cal_arm=0`.

The S16 RIGHT-reference / LEFT-follower AS5600 speed PI, wheel PI+FF, PS2 decode, R1/R2, SELECT, Voice, RAM logger and incident trace remain in the firmware. The reported RIGHT self-motion at zero MCU PWM is not resolved by replacing geometry.

## PS2 commissioning of direct steering (added 2026-10-26)

Manual D-pad LEFT/RIGHT and joystick RX no longer require editing steering arm variables in CubeIDE after each reset. They remain **OFF on boot**, and a deliberate PS2 control sequence manages only these two manual modes:

- First, release D-pad, RX and LY to neutral, release all other command buttons, release all four limit switches, and stop all four wheel motors. `debug_as5600_poll_enable` must be 0.
- **Hold START for at least 1.5 seconds**, still fully neutral. On success `steer_ps2_manual_arm_status=2`, `steer_ps2_manual_armed=1`; firmware sets `steer_manual_enable=1` and `steer_safety_motion_permit=1`, subject to a fresh LEFT/RIGHT AS5600 sample and strict calibrated hard envelope. Release START, let the firmware observe a neutral PS2 sample, then press D-pad LEFT/RIGHT or move RX to request manual steering. LEFT and RIGHT are both commanded under the existing per-side AS5600 soft-limit, NC, stall, settle and speed-sync gates.
- **Press START again** after releasing it to disarm manual steering immediately: firmware clears both permits and both steering CCRs and re-requires a neutral PS2 frame. PS2 radio loss or an NC safety trip also disarms manual steering; a trip remains latched, not cleared.
- `steer_ps2_manual_arm_status` codes: 0 idle, 1 holding START, 2 armed, 3 disarmed, 4 PS2 lost/trip, 5 not neutral, 6 NC active/uninitialized, 7 STOP/voice priority, 8 four wheels not stopped, 9 AS5600 read / geometry invalid, 10 another steering diagnostic owner busy.
- Observability: `steer_ps2_manual_arm_hold_elapsed_ms`, `steer_ps2_manual_arm_success_count`, `steer_ps2_manual_disarm_count`, `steer_ps2_manual_arm_reject_count`. Also observe `steer_manual_left_pwm/right_pwm`, `steer_manual_left_state/right_state`, `steer_sync_left_speed_raw_s/right_speed_raw_s`, and `steer_safety_trip_latched`.
- `steer_pos_enable` and `steer_cal_arm` remain 0 at boot and are **NOT automatically granted** by START; R1/R2/SELECT still require their owner-specific commissioning. LY/Up/Down simultaneously with RX remains input-decodable but physical steering in motion is still blocked by the wheel-stop interlock.
- START disarming writes MCU output compares to zero, **not** independent driver supply removal. The previously witnessed RIGHT motor self-driving while PWM was blocked remains unexplained. A human watching and releasing PS2 cannot be treated as independent emergency power isolation. For physical motor tests, a known working, accessible *total vehicle supply* cutoff is a viable independent stop when it truly removes driver power, even if STM32 turns off as well. Never unplug motor output jacks while energized. Powered motor motion and independent stop response were not tested by these source changes.

Source-only stage: S16 changed on the existing `feature/m7-s15-ps2-controls-restoration-staged` branch. Not independently cross-built in STM32CubeIDE or physically commissioned yet.


### START remains disarmed with status 9 (2026-10-26)

The old status 9 combined I2C read failure, magnet STATUS failure, and AS5600 calibrated-hard-envelope rejection. `debug_as5600_*_comm_ok=1` means the transaction completed but does **not** imply AS5600 MD=1 and ML=MH=0, nor does it prove the same frame that failed arming. The prior guard used short-circuit OR, so failure of LEFT could hide RIGHT's condition. The new firmware reads both once per deliberate START attempt and snapshots separate diagnostic bits **without relaxing any guard**.

`steer_ps2_arm_sensor_fail_mask` is a persistent failure snapshot: **1** LEFT I2C/transport; **2** LEFT magnet status invalid; **4** LEFT hard geometry/angle rejected; **8** RIGHT I2C; **16** RIGHT magnet invalid; **32** RIGHT geometry/angle rejected; **64** LEFT reader rejected for an otherwise unclassified condition; **128** RIGHT unclassified. Values may sum if both sides fail. Read `steer_ps2_arm_left_magnet_status`, `steer_ps2_arm_right_magnet_status`, `steer_ps2_arm_left_read_status`, `steer_ps2_arm_right_read_status` and `steer_ps2_arm_left_raw/right_raw` for a snapshot. RAW is prior telemetry if the new read failed. `steer_ps2_arm_sensor_fail_count` increments for each failed completed hold.

If mask=2 or 16 with I2C okay, examine AS5600 MD=0, ML=1 or MH=1 and fix physical magnet/alignment/airgap; do not edit `steer_safety_motion_permit` to skip the check. If mask=4 or 32, verify runtime calibration endpoints and actual mechanical angle. If mask=1/8, inspect I2C wiring, pullups and power stability. Existing status 9 captures alone cannot distinguish these.


## M7-S10 steering behavior restored after RIGHT interference mitigation (2026-10-26)

**User-observed hardware result:** a **1 nF capacitor** was soldered to mitigate interference associated with the RIGHT steering driver. After repeated on-vehicle tests, the earlier unintended RIGHT actuation did **not** recur. The exact capacitor connection and test waveforms were not provided, and no independent electrical measurement was made here. Do not reinterpret this observation as proof of a hard power disconnect or immunity to every later fault.

The previously protective *whole-vehicle* latch triggered by every NC limit was inconsistent with ordinary repeated steering. The current firmware policy distinguishes normal mechanical stops from sensor/electrical faults:

- Any rising NC/open edge on **LEFT MIN/MAX** immediately writes zero to **LEFT TIM12 CH2**, while **RIGHT MIN/MAX** immediately writes zero to **RIGHT TIM14 CH1**. This is per-axis **PWM cutoff**, not a physical removal of driver supply. Per-owner EXTI pending flags are still consumed, including double-limit contradictions and unexpected contacts.
- Simply touching an NC no longer sets `steer_safety_trip_latched` or forces the **four wheel drive motors** into a permanent STOP. Remaining non-NC sensor/I2C, invalid hard geometry or separate STOP conditions still have their own guards and may stop the vehicle.
- D-pad/RX is manual **toward** own MIN/MAX. Once either axis reaches its target NC or calibrated early **soft-stop** clearance, that axis cuts PWM. The opposite direction is authorized only after releasing the preceding command, observing neutral, and making a new input. When the newly requested direction is *away* from an already-asserted opposite endstop, the axis performs a bounded **<=1 second escape**. On release of the NC it cuts PWM, observes a new AS5600 quiet/settling interval, then can continue along the still-held same command if its AS5600 and limits remain valid. The RIGHT MAX escape is enabled subject to the same bounds.
- With one MIN or MAX asserted per axis, a deliberate START gesture may still arm the controllers to allow that reverse escape. Contradictory MIN+MAX on the same side blocks the arm. START remains a 1.5-second fully-neutral hold, followed by release before a new direction.
- START arms **D-pad/RX plus R1/R2**. R1 targets each separate CENTER with **±5 RAW** fine tolerance; R2 drives to each own MIN (NC arrival or ±5 RAW), independently. START toggles disarm; SELECT retains separate explicit calibration arm and is not silently enabled.
- LEFT limits remain MIN=2297, CENTER=1873, MAX=1374 and RIGHT MIN=191, CENTER=662, MAX=982. Physical contact may be pre-empted by a calibrated soft-stop, so **no NC hit is required** on every normal manual stroke.

Bench-check in this order: after a new CubeIDE Debug **Build PASS** and flash, (1) observe `steer_safety_trip_latched` stays 0 during a **single mechanically actuated NC input** while wheel command is otherwise neutral, (2) confirm independent raw/live GPIO bit 4/8/2/1, (3) confirm deliberate START can arm with only one NC asserted on a side, (4) with appropriate physical stop available confirm a fresh opposite manual command escapes and continues, and (5) check R1 at ±5 RAW and R2 MIN for both axes. Read `steer_nc_local_stop_count` / `steer_nc_local_stop_last_mask`, `steer_manual_{left,right}_state`, `steer_manual_{left,right}_pwm`, and both RAW values. Neither this source change nor static tests prove safe mechanical stopping, driver behavior, or correct electrical NC wiring on the vehicle.


## M7-S16 next bench iteration after user testing (2026-10-26)

**Actual observations supplied by the user:** four NC input tests and D-pad/RX movement gate passed on the previous `debbf1d7` firmware. Four issues remain unaccepted: RIGHT reaches the physical R_MAX NC despite the former 40-RAW manual soft margin; SELECT was not operable with normal PS2 controls because `steer_cal_arm` was still 0; LEFT and RIGHT manual turning are not synchronized in physical use; RIGHT R1 sometimes only escapes the contact on the first press, with a second press required to finish CENTER. Do not reinterpret these reports as tests of the changes described below.

Changes staged on **the same branch** for the NEXT build:
- **Manual RIGHT MAX:** a separate `steer_manual_right_max_soft_margin_raw=100U` now stops the approach earlier (100 RAW before R_MAX, soft MAX approximately 882 with the current 982 endpoint), while the RIGHT MIN margin stays 40. This is *not* a certified stopping distance or a substitute for an independent power disconnect. If contact still occurs, stop testing that direction and report RIGHT stopping RAW / NC mask; do not increase PWM to overcome it.
- **R1 one-press return:** after a previously asserted NC releases, the position controller continues only after at least 3 verified AS5600 RAW counts in the correct departure direction **or** a continuous 120-ms zero-PWM NC-release verification period with valid sensor/geometry checks. It no longer concludes `result=7` immediately when a switch opens before the encoder accumulates 3 RAW counts. The originating NC, late IRQ, wrong endpoint, I2C, hard envelope and timeout guards remain active. No evidence of smooth motion or CENTER ±5 acceptance yet.
- **SELECT deliberate PS2 commissioning:** first use START neutral hold 1.5 s to ARM steering, release START and return to neutral. Then, on a supported stand with the full mechanical sweep safe, **hold SELECT continuously for 1.5 seconds** with LY/RX/D-pad and other buttons neutral; this grants a single SELECT scan, consuming its separate `steer_cal_arm`. START itself **still does not** arm SELECT, a quick SELECT tap does not launch a sweep, and other inputs interrupt calibration. Observe `steer_cal_select_hold_elapsed_ms`, `steer_cal_select_hold_grant_count`, `steer_cal_select_hold_reject_count`, `steer_cal_result`, `steer_cal_left_stage/right_stage`, and `steer_cal_limit_fault_*`.
- **Speed matching:** RIGHT remains reference; LEFT PI compares LEFT measured RAW/s against `RIGHT_RAW_s * LEFT_stroke_RAW / RIGHT_stroke_RAW` rather than raw equality. For the existing 923/791-count strokes, equal normalized travel rate requires LEFT ~1.167 times RIGHT RAW/s. Observe `steer_sync_left_target_raw_s`, `steer_sync_left_speed_raw_s`, `steer_sync_right_speed_raw_s`, `steer_sync_error_raw_s`, `steer_sync_left_pwm_command` and `steer_sync_limit_count`. This does **not** prove matched physical steering speed under load; the tuning and output angle/gear ratios still require measurement.

**Test order:** verify target CubeIDE Debug build; flash only after confirming the clean intended source; first inspect NC/AS5600 with PWM off, then low-risk D-pad RIGHT/LEFT with ample free travel and abort if RIGHT moves unexpectedly or still strikes R_MAX. Once R_MAX clearance is demonstrated, test RIGHT R1 from a legitimately actuated NC and check both final CENTER RAW bands (LEFT 1868–1878, RIGHT 657–667). Only then intentionally run the full-range SELECT calibration on the suspended, unobstructed vehicle with a working total-driver supply disconnect. Measure sync in mid-stroke, not near start/settling or soft stops.
